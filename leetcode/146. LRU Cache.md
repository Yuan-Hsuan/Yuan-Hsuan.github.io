## 🎙️ Naive Solution

The naive approach is to use a standard Doubly Linked List to store the key-value pairs. While inserting a new pair at the front takes O(1) time, accessing an element requires scanning the entire list, resulting in an O(N) time complexity for the get operation. This fails to meet the strict O(1) requirement for both get and put.

## 🚀 Pitch

### The Bottleneck Observation (時間複雜度與任意節點刪除)

The core bottleneck is the O(N) lookup time. To make retrieval O(1), we need a Hash Map. However, a standard Hash Map does not maintain insertion or access order. To evict the Least Recently Used (LRU) element in O(1), we must also maintain a Doubly Linked List. A singly linked list is insufficient because deleting a node in the middle of the list would still require O(N) time to find its predecessor.

### The Strategy: Hash Map + Doubly Linked List (資料結構協同)

To achieve O(1) for both operations, we combine a Hash Map (std::unordered_map) and a Doubly Linked List (std::list). The hash map stores the key, and its value is an iterator (pointer) pointing directly to the corresponding node in the doubly linked list. This allows us to locate any node in O(1) time and perform instant updates.

### The Precise Execution & Heap Optimization (記憶體不重配置與指標轉移)

When a key is accessed or updated, it must be moved to the head of the list. A naive implementation deletes the node (list.erase) and inserts a new one (list.push_front), which triggers slow heap allocations (new/delete).
To achieve true production-grade performance, we use std::list::splice to instantly move the node to the front by re-linking pointers, completely avoiding memory allocation overhead.

**Complexity**
- **Time — O(1) per operation:** hash-map lookup plus a `splice`/`push_front`/`pop_back`, all O(1).
- **Space — O(capacity):** the list and map together hold at most `capacity` entries.

## 🛠️ Optimization (原始程式碼待優化區)

* 避免無謂的記憶體配置 (Use std::list::splice instead of erase + push_front)：

    * 原著寫法： li.erase(li_itr); li.push_front({key, value});
    * 效能瓶頸： erase 會釋放記憶體，push_front 會在 Heap (堆積) 上重新配置一塊 Node 空間。頻繁的 put / get 會導致嚴重的記憶體碎片化 (Memory Fragmentation) 並降低效能。
    * 優化建議： 使用 C++ STL 的 std::list::splice。它可以直接在 O(1) 時間內將指定迭代器指向的節點，拔除並插到鏈結串列的最前面，完全不觸發任何 new / delete！

* 致命的變數遮蔽警告 (Variable Shadowing)：

    * 原著寫法： 在 put(int key, int value) 中，當容量超出時，你宣告了 int key = li_itr->first;。
    * 錯誤風險： 內層的 key 遮蔽了參數列的 key。雖然在這邊邏輯剛好正確，但在嚴格的編譯器中（如 -Wshadow）會直接編譯失敗，這在面試中是極大的扣分項。
    * 優化建議： 重新命名為 key_to_evict。

```c++
#include <unordered_map>
#include <list>

using namespace std;

class LRUCache {
private:
    int capacity;
    // 儲存實際的 {key, value} 節點
    list<pair<int, int>> li;

    // 儲存 key 對應到 list 中節點的 iterator (指標)
    unordered_map<int, list<pair<int, int>>::iterator> mp;

    // 💡 封裝美學：將「移到最前面」的邏輯獨立出來，保持 get/put 乾淨
    void moveToHead(int key, int val, list<pair<int, int>>::iterator itr) {
        // 更新節點的值 (因為可能是 put 觸發的更新)
        itr->second = val;
        // 🌟 核心優化：使用 splice 進行指標移轉，不涉及任何記憶體配置與銷毀
        li.splice(li.begin(), li, itr);
        // 更新 Hash Map 的對應關係
        mp[key] = li.begin();
    }

public:
    LRUCache(int c) : capacity(c) {
        // 🛡️ 防禦性編程：防範容量無效的狀況
        if (capacity <= 0) {
            capacity = 1;
        }
    }

    int get(int key) {
        auto itr = mp.find(key);
        // 如果找不到，直接回傳 -1
        if (itr == mp.end()) return -1;

        // 如果找到了，將該節點移到最前面，並回傳值
        int val = itr->second->second;
        moveToHead(key, val, itr->second);

        return val;
    }

    void put(int key, int value) {
        auto itr = mp.find(key);

        if (itr != mp.end()) {
            // 情境 1: Key 已經存在，更新值並移到最前面
            moveToHead(key, value, itr->second);
        } else {
            // 情境 2: Key 不存在，新增一個節點到最前面
            li.push_front({key, value});
            mp[key] = li.begin();

            // 如果超出容量，淘汰最末端 (Least Recently Used) 的節點
            if (li.size() > capacity) {
                // 取得最後一個節點的 key
                int key_to_evict = li.back().first; // Bug Fix: 避免與參數 key 發生 Variable Shadowing

                // 從 map 與 list 中移除
                mp.erase(key_to_evict);
                li.pop_back();
            }
        }
    }
};
```

## 🛡️ Defensive Coding (防禦性編程)

* 變數遮蔽警告防護 (Variable Shadowing Prevention)：
在 C++ 中，絕對不要在局部範疇 (Local Scope) 中宣告與函數參數同名的變數。這不僅會造成編譯 Warning，還極容易在後續修改程式碼時引發不易偵測的邏輯 Bug。

* 零與負容量防護 (Zero/Negative Capacity Guard)：
在建構子中加上 if (capacity <= 0) capacity = 1;。在實際工業級應用中，外部輸入的參數不可信。防止初始化一個空 Cache 導致後續除以零或 Null Pointer 的崩潰。
